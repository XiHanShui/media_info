## Question

macOS 端的验收靠什么路径？这件事只有人能回答，而且它卡着后面两张票（CI 构建、分发形态），必须先落地。

需要人工确认并回答的几件事：

- **本机有没有 Mac**（或有没有可远程访问的 Mac）？如果没有，验收只能靠 CI。
- **GitHub Actions 的 `macos-latest` runner 能不能满足验收**？关键是：验收需要跑 GUI 界面吗，还是只需要"能构建出可执行产物、能在命令行启动不崩"就够？如果需要人看界面，CI 产出的产物得由人下载到 Mac 上手动验证——那要如实写进验收流程。
- **需不需要自托管 runner**（有 Mac 且希望 CI 产物直接可测时）？
- 附带：`gh` 已登录 `XiHanShui` 账号，仓库是公开的 `XiHanShui/media_info`——CI 权限上没有障碍，这一点不用再问。

**产出**：一条确定的 macOS 验收路径（写清楚"谁、在哪、怎么验"）。

**注意**：这是**动手确认**，不是让你做技术选型。别在这票里纠结 CI 怎么写——那是票 10 的事。

## Answer

**平台推进顺序**：Windows 优先——先把 Windows 跑通，macOS 随后由用户自己动手验证。macOS **仍在 MVP 范围内**，只是不与 Windows 并行推进。

**macOS 验收路径**：CI 的 `macos-latest` 只负责"能构建出产物"这一层；**macOS 上的运行行为不由 CI 验收**，由用户在自己的 Mac 上验。不需要自托管 runner。

**验收标准（Windows 与 macOS 统一）**：构建成功 + 手动点过主流程——启动应用 → 打开一个文件 → 同时看到语义字段与结构树 → 展开任意一个块并看到它的原始 hex。

**对下游票的影响**：

- 票 10（CI）：Windows 与 macOS 都进矩阵，但 Windows 产物是首要验收对象；macOS 产物只需构建成功、不做自动冒烟。
- 票 11（分发形态）：macOS 侧"用户怎么验"已有答案——用户自己验，不需要额外验证通道。
